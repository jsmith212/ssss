# ssss — Super Simple Sample Station

A desktop sample manager: one library folder (cloud-sync friendly), nested
tags, collections and packs, automatic BPM/key detection, instant search,
tempo- and key-matched preview, and drag-out into a DAW.

Built with Go, [Wails v3](https://v3.wails.io) (pinned to v3.1.0) and
Svelte 5 + TypeScript.

## Development

Requirements:

- Go 1.26 or newer and Node.js
- the Wails CLI, pinned to the same version as the Go module:
  `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0`
- on Linux, only for building outside the Flatpak (see Running): the GTK 4
  and WebKitGTK 6.0 development packages and `pkg-config`
- Chromium, only for the two browser-driven tests (`chromium` on `PATH`, or
  its path in `$CHROMIUM`)

The Linux checks also run in a container with the whole toolchain, which is
what CI uses:

```sh
docker build -t ssss-ci build/ci
docker run --rm -u "$(id -u):$(id -g)" -v "$PWD":/src ssss-ci build/ci/check.sh
```

| Task | Command |
| --- | --- |
| Build the app (`bin/ssss`) | `wails3 build` |
| Run with live reload | `wails3 dev` |
| Frontend only, in a browser, against a mock backend | `cd frontend && npm install && npm run dev` |
| Type-check the frontend | `cd frontend && npm run check` |
| Frontend tests | `cd frontend && npm test` |
| Go tests and vet | `go test ./... && go vet ./...` |
| UI smoke test (headless Chromium, mock backend) | `cd frontend && npm run smoke` |
| Audio engine end-to-end test (headless Chromium) | `cd frontend && npm run e2e:audio` |
| Regenerate TypeScript bindings | `wails3 generate bindings -clean=true -ts -i` |

`wails3 build` regenerates the bindings and builds the frontend before
compiling, so it is the only command a fresh checkout needs. The generated
`frontend/bindings` are kept in the repository all the same: the frontend's
own check, tests and smoke test import them and do not run the generator.

## Running

On Linux the app is built and run as a Flatpak. The GNOME runtime supplies
GTK 4, WebKitGTK 6.0, the GSettings schemas and GStreamer.

One-time setup:

```sh
flatpak install flathub org.gnome.Platform//51 org.gnome.Sdk//51 \
  org.freedesktop.Sdk.Extension.golang//26.08 \
  org.freedesktop.Sdk.Extension.node24//26.08 \
  org.flatpak.Builder
```

Build, install for the current user, and run (from the repository root):

```sh
flatpak run org.flatpak.Builder --user --install --force-clean \
  bin/flatpak-build build/flatpak/com.ssss.app.yml
flatpak run com.ssss.app
```

The build downloads Go modules and npm packages. Inside the Flatpak, settings
and cache live under `~/.var/app/com.ssss.app/`.

A bare `wails3 build` produces `bin/ssss`, which needs GTK 4, WebKitGTK 6.0
and the GStreamer *base* and *good* plugins installed on the system.

Only one copy runs per user; starting it again brings the running window to
the front.

## Where things live

| What | Where |
| --- | --- |
| The library: audio in `Samples/`, metadata in `_library/` | the folder you choose; safe to keep in a synced folder |
| Removed samples and merged conflict copies | `<library>/_library/trash/`; never emptied by the app, delete its contents by hand to reclaim the space |
| Settings (per machine, not synced) | `<config dir>/ssss/settings.json` |
| Search index, waveform peaks (per machine, disposable) | `<cache dir>/ssss/<library id>/` |

`<config dir>` and `<cache dir>` are `~/.config` and `~/.cache` on Linux,
`~/Library/Application Support` and `~/Library/Caches` on macOS, `%AppData%`
and `%LocalAppData%` on Windows; `SSSS_CONFIG_DIR` and `SSSS_CACHE_DIR`
override the `ssss` folders. Deleting the cache folder is always safe:
Settings → Rebuild Cache does the same for the index.

The mock backend (`frontend/src/lib/api.mock.ts`) generates a deterministic
20,000-sample library with synthesised audio, so the whole interface works in
a plain browser at <http://127.0.0.1:5173>. Add `?state=none`,
`?state=unavailable`, `?state=readonly` or `?state=empty` to see the other
library states and `?n=50000` to change the library size. The mock is a
development tool only: `npm run dev`, the smoke test and a debug build
(`npm run build:dev`) have it, the production bundle does not.

## Layout

```
main.go              Wails wiring: window, asset handler, service, file drops
internal/model       types shared with the frontend
internal/api         the service bound to the frontend
internal/...         library format, index, audio, analysis, ingest, drag-out
frontend/src         Svelte app; lib/api.ts is the only door to the backend
frontend/bindings    generated by wails3, do not edit
build/               Wails packaging assets and Taskfiles
```
